# mersey-kmp-jobs

Долгие задачи для Kotlin Multiplatform: **Android, iOS, Web (Wasm)**.

Работа, которая идёт минутами, не должна зависеть от экрана, с которого её запустили,
и не должна начинаться заново после того, как систему решила выгрузить приложение.
Библиотека даёт для этого рантайм; что именно считается внутри задачи, она не знает.

## Что решает

Обычная корутина экрана умирает вместе с экраном. Перенести её в область уровня
приложения мало: приложение уходит в фон, и система вправе убить процесс. Поэтому нужны
три вещи сразу — работа вне экрана, просьба к системе не убивать процесс, и сохранённый
прогресс на случай, если убили всё-таки.

Прогресс сохраняется **пошагово**. Незавершённый запрос продолжить невозможно, его можно
только повторить — но повторяется именно он, а не всё, что было сделано до него.

## Что внутри

```
jobs-core/
├── commonMain/
│   ├── JobSpec.kt             вид работы: имя, параметры, тело
│   ├── ExecutionStrategy.kt   Parallel | Sequential — идут ли задачи вида по очереди
│   ├── RetryPolicy.kt         когда повторять после временной ошибки
│   ├── JobScope.kt            разметка работы на шаги + доклад о ходе
│   ├── JobRunner.kt           запуск, наблюдение, отмена, восстановление
│   ├── RealJobRunner.kt       рантайм: область корутин, реестр, очередь, удержание процесса
│   ├── RealJobScope.kt        контрольные точки шагов
│   ├── JobHandle.kt           ручка запущенной задачи + await() + исключения рантайма
│   ├── JobState.kt            Running | Waiting | Success | Failed | Cancelled
│   ├── JobUseCase.kt          обёртка для экрана: колбэки, invoke, ключ замены
│   ├── JobFlowUseCase.kt      обёртка для экрана: ход работы потоком событий
│   ├── JobCrudUseCase.kt      создание, изменение, удаление сущности — отправленной и нет
│   ├── JobEvent.kt, JobId.kt, JobProgress.kt
│   ├── storage/               интерфейс хранилища + реализация в памяти
│   └── hold/ProcessHold.kt    интерфейс удержания процесса + заглушка
├── androidMain/               сервис на переднем плане (dataSync)
└── iosMain/                   beginBackgroundTask
```

Приложение приносит две вещи: **хранилище** (у него уже есть база) и **удержание процесса**
под свою платформу. Своей базы библиотека не заводит и своих строк для уведомления не имеет.

Хранилище обязано:

- сохранять каждое поле `JobRecord`, включая `createdAt`, `ownerKey` и `isFailed`;
- отдавать `activeJobs()` **по возрастанию `createdAt`** — иначе после перезапуска очередь
  выстроится в случайном порядке;
- в `setFailed(id)` снимать с записи «активна» и «откатывается», ставить «упала» и забывать
  её шаги.

## Как пишется задача

```kotlin
object SortLibraryJob : JobSpec<SortParams, SortResult> {

    override val type = "sort-library"
    override val paramsSerializer = SortParams.serializer()

    override suspend fun JobScope.execute(params: SortParams): SortResult {
        val playlists = step("playlists") { api.playlists(params.userId) }

        val tracks = playlists.flatMapIndexed { index, playlist ->
            // Имя шага должно совпадать от прохода к проходу — отсюда номер
            step("tracks-$index") { api.tracks(playlist.id) }
        }

        // Данные каталога на диск не ложатся: поставщик разрешает держать их
        // только на время показа
        val genres = memoryStep("genres") { beatport.genresFor(tracks) }

        report(SortProgress.Building)
        return SortResult(group(tracks, genres))
    }
}
```

Шаг `step` выполняется один раз за всю жизнь задачи: при повторном проходе его результат
приходит из хранилища. Шаг `memoryStep` переживает перезапуск задачи, но не процесса.

## Запуск

```kotlin
val runner = RealJobRunner(
    specs = listOf(SortLibraryJob),
    storage = MyDatabaseJobStorage(db),
    hold = AndroidProcessHold(context, JobNotification(...))   // на iOS — IosProcessHold()
)

val handle = runner.start(SortLibraryJob, SortParams(userId))
handle.state.collect { state -> /* показать прогресс */ }
```

Повторный `start` с теми же параметрами не заводит вторую задачу — возвращает ту же ручку.
Экран, открытый заново, забирает её по `JobId` через `runner.handle(id)`.

`runner.restore()` вызывается при старте приложения и при возвращении его на экран: он
поднимает работу, прерванную перезапуском или системой.

## Очередь: задачи по одной

По умолчанию задачи одного вида идут одновременно, каждая в своей корутине. Если порядок
важен серверу — например, сообщения, написанные без сети, — вид работы объявляет очередь:

```kotlin
override val executionStrategy = ExecutionStrategy.Sequential()
```

- Задачи этого вида выполняются **строго по одной, в порядке создания**. Следующая не
  начинается, пока не закончится предыдущая: успехом, ошибкой или отменой.
- Очередь одна на **весь вид работы**. Сообщение в чат Б ждёт, пока уйдёт застрявшее
  сообщение в чат А.
- Стоящая в очереди задача **показывает состояние первой**. Первая ждёт сеть — все стоящие
  за ней тоже в `Waiting` с той же ошибкой, и экран получает `onScheduled`. Первая
  выполняется — стоящие в `Running`. Попытки у стоящих не считаются, процесс ради них не
  удерживается.
- Порядок переживает перезапуск: у записи есть `createdAt`. Повторный `start` с теми же
  параметрами сохраняет место в очереди. Две задачи никогда не получают одно время:
  вторая сдвигается на миллисекунду.

Что делает окончательная ошибка первой задачи с остальными, задаёт `onFailure`:

| | что происходит |
|---|---|
| `QueueFailure.Continue` (по умолчанию) | падает только она, остальные идут дальше |
| `QueueFailure.FailRest` | все стоящие за ней падают, не пробуя: для каждой вызывается `compensate`, в состояние приходит `JobQueueFailedException` с исходной ошибкой в `cause` |

```kotlin
override val executionStrategy = ExecutionStrategy.Sequential(QueueFailure.FailRest)
```

`FailRest` — для работы, которая бессмысленна без предыдущей: «создать сообщение», за ним
«отредактировать его же». Задача, созданная после ошибки, начинает очередь заново.
**Отмена ошибкой не считается** и затрагивает только отменённую задачу.

Ограничения:

- Время берётся с часов устройства. Если перевести часы назад, пока в очереди лежат
  незаконченные задачи, после перезапуска новые встанут раньше старых. Пока процесс жив,
  порядок не ломается.
- Если процесс убит посреди `FailRest`, задачи, до которых отмена не дошла, после
  перезапуска выполнятся как обычные.

## JobUseCase: работа из экрана

`JobUseCase` — обёртка над одним видом работы для экрана или стора.

```kotlin
class SendMessageInteractor(runner: JobRunner, job: SendMessageJob) :
    JobUseCase<Message, MessageParams>(runner, job)
```

**С колбэками.** Кроме успеха и ошибки есть третий исход — `onScheduled`: работа ещё не
сделана, но запланирована и пройдёт, когда уйдёт препятствие. Отмена молчит: кто отменил,
тот и знает.

```kotlin
sendMessageUseCase.execute(
    coroutineScope = scope,
    params = params,
    onScheduled = { error -> /* показать «ждёт сеть» */ },
    onComplete = { message -> },
    onError = { error -> }
)
```

**Прямо из корутины**, как `CoroutineUseCase`:

```kotlin
val message = sendMessageUseCase(params)
```

| исход работы | что делает вызов |
|---|---|
| успех | возвращает результат |
| окончательная ошибка | выбрасывает её |
| ждёт сеть | не возвращается, пока работа не выполнится |
| работу отменили | выбрасывает `CancellationException` с `JobCancelledException` в `cause` |

Отмена вызывающей корутины прекращает только ожидание — работа продолжается в рантайме.
Если ловить все ошибки через `catch (e: Throwable)`, `CancellationException` нужно
пропускать дальше.

**Наблюдение за всей работой вида** — `observeOngoing`. Приходят уже идущие работы,
упавшие, которые вид [хранит](#упавшая-работа-хранится), и **каждая работа, запущенная
позже** — с этого экрана или с любого другого, — пока жив `coroutineScope`. Колбэки идут
вместе с параметрами работы:

```kotlin
sendMessageUseCase.observeOngoing(
    coroutineScope = scope,
    ownerKey = "chat-$chatId",                  // null — вся работа вида
    onScheduled = { params, error -> },         // ждёт: нет сети, очередь
    onRunning = { params -> },                  // снова пошла
    onComplete = { params, message -> },
    onError = { params, error -> }
)
```

Одна работа может много раз переходить между `onScheduled` и `onRunning`, пока сеть то есть,
то нет. Отменённая работа замолкает.

## Ключ владельца

Работе можно дать **ключ владельца**: задача, чат, поле. Он нужен для двух вещей — найти
работу одного владельца и заменить её.

```kotlin
class CreateCommentInteractor(runner: JobRunner, job: CreateCommentJob) :
    JobUseCase<Comment, CommentCreate>(runner, job) {

    override fun ownerKeyOf(params: CommentCreate) = "task-${params.taskId}"
}
```

- Ключ считается **из параметров** каждого вызова, поэтому один экземпляр обслуживает многих
  владельцев. Если ключ одинаков для всех вызовов, `ownerKeyOf` возвращает константу.
- Работа принадлежит **ключу, а не экземпляру**: два экземпляра с одним ключом ведут себя
  как один, ради этого не нужно добиваться одного объекта из DI.
- Ключ действует **в пределах вида работы**: одинаковые ключи у разных видов не мешают.
- Ключ хранится в записи и переживает перезапуск.
- `observeOngoing(ownerKey = ...)` видит **только работу этого владельца**.

### Замена: важен только последний запрос

Пользователь трижды без сети поменял статус задачи — на сервер должен уйти только последний.
Для этого `replacesPrevious = true`: новая работа с тем же ключом отменяет незаконченную —
вместе с откатом `compensate` — и только потом стартует.

```kotlin
class SetTaskStatusInteractor(runner: JobRunner, job: SetTaskStatusJob) :
    JobUseCase<Task, SetTaskStatusInteractor.Params>(runner, job, replacesPrevious = true) {

    // Доска двигает много задач: смена статуса одной не отменяет смену другой
    override fun ownerKeyOf(params: Params) = "task-${params.taskId}"
}
```

- Без ключа замена ничего не делает.
- **Те же параметры не отменяются** — это та же работа, раннер вернёт её и разбудит, если
  она ждёт.

Ограничения:

- Отмена не возвращает уже отправленный запрос — отменяется ожидание ответа и то, что шло
  бы после него.
- Работу, пережившую выгрузку процесса, раннер знает только после `restore()`. Вызов до
  него старую работу не отменит.
- Одинаковые параметры с разными ключами — всё ещё одна работа: второй присоединится к
  первой, ключ останется от первой.

## Удалить и отредактировать то, что ещё не ушло

Для работы, которую человек видит и может передумать: комментарий, написанный без сети.

```kotlin
createCommentUseCase.cancel(params)                       // «Удалить»
createCommentUseCase.replace(old = params, new = edited)  // «Редактировать»
```

- Обе операции срабатывают, **только пока запрос не в пути**: работа ждёт сеть, стоит в
  очереди или упала. Если запрос уже ушёл, они возвращают `false` и ничего не трогают —
  отмена не вернула бы то, что сервер уже сделал. Проверка и отмена идут под одним замком
  раннера: работа не успеет начать отправку между ними.
- `cancel` — отмена с откатом, как `runner.cancel(id)`.
- `replace` — старая работа отменяется с откатом, новая **встаёт на её место в очереди**:
  получает её время создания. Новая приходит в `observeOngoing` как любая другая.

## Упавшая работа хранится

По умолчанию работа, упавшая окончательно, забывается. Для работы, про которую решает
человек, вид может её хранить:

```kotlin
override val keepsFailed = true
```

- Откат `compensate` выполняется **сразу при ошибке**, как обычно. Запись остаётся с пометкой
  «упала», шаги забываются.
- Упавшая работа приходит в `observeOngoing` через `onError` — и сразу, и на экране,
  открытом заново, и после перезапуска приложения. После перезапуска сама ошибка не
  сохраняется: приходит `JobFailedBeforeRestartException`.
- «Повторить» — обычный `start` / `execute` с теми же параметрами: работа идёт под своим id
  и **со своим местом в очереди**. Повтор выполняется поверх уже откаченных данных.
- «Удалить» — `cancel`: работа забывается без второго отката.
- В очереди `Sequential` упавшая работа **не держит** следующих.
- `restore()` упавшую работу не поднимает, только возвращает в реестр как упавшую.

## JobCrudUseCase: сущность, которую создают, меняют и удаляют

Комментарий или сообщение живут в двух видах, и каждое действие для них идёт своим путём:

| | не отправлена: параметры создания ждут в работе | отправлена: есть на сервере |
|---|---|---|
| создать | `create` | — |
| наблюдать | `observeCreating(ownerKey)` | — |
| изменить | `updateCreating(old, new)` — `replace` работы создания, место в очереди сохраняется | `update(params)` — своя работа изменения |
| удалить | `deleteCreating(params)` — `cancel` работы создания, сервер ничего не узнаёт | `delete(params)` — своя работа удаления |
| повторить упавшую | `retryCreating(params)` | — |

```kotlin
class TaskCommentsInteractor(
    create: CreateCommentInteractor,
    update: UpdateCommentInteractor,
    delete: DeleteCommentInteractor
) : JobCrudUseCase<Comment, CommentCreate, CommentUpdate, Id>(create, update, delete)
```

- Класс ничего не знает о структуре параметров. Новые параметры при изменении неотправленной
  сущности собирает наследник: `updateCreating(old, old.copy(body = text))`.
- **Параметры создания обязаны быть уникальными** — несите в них локальный id. Иначе два
  одинаковых комментария станут одной работой, а `updateCreating` и `deleteCreating` не
  отличат один от другого.
- `updateCreating` и `deleteCreating` ничего не делают, если запрос уже в пути. Для
  `deleteCreating` это значит, что `onDeleted` не придёт.
- У операций над неотправленным суффикс `Creating`, а не перегрузка: параметры создания и
  удаления могут оказаться одного типа.

## Что даёт каждая платформа

| | чем удерживается процесс | сколько живёт |
|---|---|---|
| Android | сервис на переднем плане, тип `dataSync` | пока идут задачи; с Android 15 у `dataSync` есть суточный лимит |
| iOS | `beginBackgroundTask` | десятки секунд после ухода в фон, дальше — пауза до возвращения |
| Wasm | ничего | пока открыта вкладка |

Android 12 и новее не позволяют поднять сервис на переднем плане из фона: `start` и
`restore` вызываются, когда приложение на экране. Уведомление на Android 13 и новее
покажется только с разрешением `POST_NOTIFICATIONS` — спрашивает его приложение,
без разрешения сервис работает молча.
